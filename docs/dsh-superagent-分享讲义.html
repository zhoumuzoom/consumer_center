02 SCENARIO WHY GAPrequest ≠ PR

一个需求，从提出到合并要跨过多少断点

AI Coding 让写代码变快了，但把改动搬进仓库、验证回归、写 PR、等 review 仍然要人；
任何一个环节断掉，交付就停在半路。

AI Coding

  • 在群里看到 bug 报告或者改动点
  • 打开 AI IDE，贴日志、代码和上下文
  • 让 AI 生成代码，自己判断取舍
  • 把改动搬进仓库，手工验证相邻路径
  • 写 PR 描述，补截图
  • 等 review、等合并

dsh-superagent + 飞书接需求

  • @ 机器人，附背景、期望、验收标准
  • Ticket 自动生成，独立 worktree
  • Worker 定位改动点，最小改动
  • 回归相关路径，补必要验证
  • PR 带改动说明、影响面、验证记录
  • 回复飞书线程，合并收尾

本次分享的主线：把飞书里的一条报告或改动点，变成 GitHub 上可审查、可合并的 PR。

先让听众认同：左边的 AI Coding 已经把"写代码"加速了，但贴上下文、搬改动、验证、写 PR 这些动作还在人手里。

右侧这条闭环就是 dsh-superagent 的价值；bug 和优化需求走同一条闭环，区别只在 Ticket 里的任务描述。

03 SETUP T+0 WHATone bundle

dsh-superagent 是什么，怎么装

它就是上一页那条闭环的落地形态：跑在 DSH 上的一个 bundle，飞书入口，GitHub 交付；每张 Ticket 在独立 worktree 里跑完，回一个 PR。

运行形态
形态DSH bundle · 独立 profile superagent
执行一 Ticket = 一 worktree + 一 session + 一分支
交付PR + 原线程回复；合并权留在人手里

不是依赖库，不是多租户服务，不碰生产；官方定位 research prototype。

环境 · 一台 macOS / Linux
Node ^22.19 / 24 pnpm 11 git 2.32+ Python 3.8+ tmux gh 2.48+ lark-cli 1.0.90+ dsh ^0.2.1-alpha.2

账号：GitHub Agent 账号（Write）· 飞书自建应用 · DeepSeek 账号。

# 源码 → 构建 → 建 profile → 挂 bundle → 启动
git clone https://github.com/deepseek-ai/dsh-superagent-prototype.git
cd dsh-superagent-prototype && pnpm install && pnpm build
dsh superagent --from-default-profile web --dump-config > /dev/null
dsh plugin --profile superagent add "link:$PWD"
python3 scripts/dsh-superagent start
也可以一行对话对 DSH 说「安装 dsh-superagent 和它的环境」，克隆、构建、建 profile、挂插件它都会做；但版本和账号仍要能看懂。

接着上一页那条闭环往下讲：先用 30 秒建立心智模型——它不是一个聊天工具，而是 DSH 上的一个 bundle；一个实例只服务一个仓库。

环境清单念一遍即可，重点是 Node 22.19+/24、pnpm 11、gh 2.48+、lark-cli 1.0.90+，以及 dsh 满足 bundle 的 engines。

安装五步：clone → install/build → 建 profile → link plugin → start；启动后面板在 127.0.0.1:3082。最后补一句：也可以让 DSH 一句话代装，但它跑的是同一套检查，知道清单才知道卡在哪。

04 GITHUB SETUP BIND1 account

给它一个自己的 GitHub 身份

装完还差一步：给它一个能推分支、开 PR、读通知的 gh 登录，而不是往环境变量里塞 token。

  • 01 专用 wrapper · ~/.local/bin/gh-agent 只做一件事：把 GH_CONFIG_DIR 指到 ~/.config/gh-agent，和你自己的 gh 互不覆盖。
  • 02 登录一次 · 浏览器 device code 完成授权，顺手勾上 git 凭据；repo 推分支开 PR，workflow 改 CI。
  • 03 面板绑定 · Sources → GitHub 填 owner/name 与 CLI 绝对路径；保存即验账号、验推送权限，并生成 worker 的 git 配置。
  • 04 补齐 notifications · 少了它，Source 拉不到账号通知，群里 @ 了也不会变成 Ticket；用 auth refresh 补，再 auth status 复核。
# 只切配置目录的 wrapper，不动你自己的 gh 登录
mkdir -p ~/.local/bin
cat > ~/.local/bin/gh-agent <<'EOF'
#!/bin/sh
GH_CONFIG_DIR="$HOME/.config/gh-agent" exec gh "$@"
EOF
chmod +x ~/.local/bin/gh-agent
gh-agent auth login

worker 只用这个 CLI，并清掉 GH_TOKEN / GITHUB_TOKEN。本机为了让 PR 作者可辨认直接用了 zhoumuzoom；更稳妥的做法是单开一个 agent 账号。

gh-agent auth login
github.com/login/device
gh-agent auth status

三张都是真实终端操作，点击任意一张放大。

这一页讲“装完到能用”之间漏掉的那一步：GitHub 关联。核心不是 token，而是一个独立的 gh 登录身份——它决定 PR 作者是谁、通知怎么读。

四个动作：wrapper 只切 GH_CONFIG_DIR；auth login 走浏览器 device code，记得同时授权 git 凭据，repo 用于推分支开 PR、workflow 用于改 CI；面板 Sources → GitHub 填仓库和 CLI 路径，保存时 setup 会验账号与推送权限；最后补 notifications——这是唯一不会在保存时报错、却会让整条链路静默失效的 scope，少了它群里 @ 完什么都不会发生。

三张截图都是真实操作：登录四问、设备码、auth status 输出。补一句风险：本机为了作者可辨认直接用了 zhoumuzoom，更稳妥是单开一个 agent 账号。这一段正是我踩过坑的地方——scope 少了 notifications，Source 就一直读不到 @ 提及。

05 FEISHU SETUP BOTlong conn

飞书机器人是怎么接进来的

需求从飞书进来：一个自建应用 + 一条长连接 + 一份 bot 专属的 CLI 配置。

接入配置
应用企业自建应用，启用机器人能力
事件im.message.receive_v1，长连接
CLIlark-cli，独立 bot-only 配置目录

真实终端：appSecret 由 stdin 读入、不回显；strict-mode 之后 lark-cli 只能用机器人身份。

本机命令 
LARKSUITE_CLI_CONFIG_DIR=~/.lark-cli-dsh-superagent \
lark-cli event consume \
  im.message.receive_v1 --as bot

lark-cli 只用机器人身份，不继承个人登录；事件走长连接进入 DSH，不需要公网回调地址。

机器人加入群后，成员列表里才会出现它；@ 列表同理。

这一页讲"飞书到底怎么接"。三个关键点：自建应用要开机器人能力；事件订阅必须是长连接；lark-cli 必须用独立的 bot-only 配置，不能复用个人登录。

右侧截图就是这台机器上的真实记录：独立配置目录、appSecret 走 stdin、strict-mode 锁成 bot。

如果听众自己搭，最常见的卡点就是事件订阅方式选错，以及拿个人 lark-cli 配置去跑。

06 ARCH HOW FLOW3 sides

飞书、DSH、GitHub 三边怎么接

GitHub 与飞书都接好了，回到全景：一条 @ 消息怎么走到 PR。

飞书侧只负责"收到一条 bug 报告"：机器人 + lark-cli 长连接，把事件交给 Source。

DSH 侧用 Policy 决定"谁能报 bug"，Ticket 隔离执行；Worker 以 gh-agent 身份操作 GitHub，交付 PR。

这张图是全场的技术骨架：左边飞书，中间 DSH profile，右边 GitHub 与交付。

强调两个隔离：来源隔离（飞书事件与 GitHub 操作分开）、执行隔离（worktree + 分支）。出错不会污染主分支。

07 PIPELINE T+0 7stages

一条 bug 报告的 7 个阶段

阶段标记，不代表真实耗时；每一步都有可检查的产物。

  1. T+0飞书群 @机器人：复现步骤、期望行为、实际行为report
  2. T+1superagent 执行：Policy 校验（open_id 在白名单、mention 真实、来源是人）+ Ticket 生成（独立 worktree、agent/* 分支）superagent
  3. T+3复现：按步骤跑，读日志/测试，确认根因reproduce
  4. T+4修复：最小改动，不顺手重构fix
  5. T+5回归：原场景 + 相邻路径 + 构建/测试verify
  6. T+6PR + 飞书线程回复：开 PR，把结论回到原会话deliver
  7. T+7合并 PR：评审通过后合并，Ticket 结束merge

真实基线：同一条链路已在 3 个真实工单上跑通（功能/文档），从 @ 到合并最快 15 分 34 秒；bug 修复走同一流程。

这一页把"修 bug"拆成 7 个可观察的阶段。重点不是时间，而是每个阶段都有产物：Trigger、Ticket、根因、修复 diff、回归记录、PR、合并记录。

注意第 2 步：Policy 校验和 Ticket 生成其实是同一个动作——source 收下消息后先过白名单，通过了才开 Ticket，讲解时并成一句"superagent 执行"更好懂。

最后两步也拆开讲：PR 与飞书回复是"交付"，合并是"人的决定"，别混成一个阶段。

真实基线那句话要讲清楚：15 分 34 秒来自功能改动的真实运行，不是这次 bug 修复的计时。

08 FIX T+3 4actions

Ticket 里，Agent 具体做什么

不是"把报错丢给模型"，而是按修复流程逐项留下证据。

01 / REPRODUCE

复现

起本地环境，按报告步骤确认实际行为；复现不了先问，不猜。

产物复现步骤 + 失败日志

02 / LOCATE

定位

从入口沿调用链读代码，用日志/测试二分缩小范围，写清根因。

产物根因说明 + 影响面

03 / FIX

修复

只改必要文件，保持最小 diff；不顺手重构、不改无关样式。

产物最小修复 diff

04 / VERIFY

回归

原 bug 场景 + 相邻路径；UI 变化附 Before/After；验证写进 PR。

产物回归记录 + 证据

这四步对应 worker 的 scope / delivery 约束：改动越小，review 成本越低。

这一页回答"Agent 到底怎么修 bug"。四个动作里，复现和定位通常比改代码更花时间；也是最能体现 Agent 价值的地方。

强调"最小 diff"：不是不会重构，而是 bug 修复场景下主动克制。

10 POLICY GATE AUTH3 checks

谁可以报 bug

权限不靠提示词自觉，而是三道硬门槛；任何一道不满足都不会生成 Ticket。

01 / ALLOWED

白名单

飞书用户 open_id 必须显式写进 Policy。名单为空时，谁都不能发起。

02 / ADDRESSED

真的 @ 到

事件里的 mentions 必须包含机器人 open_id。手打的 @ 只是文本，会被判定 no_mention。

03 / HUMAN

必须是人

Agent 自己的消息被判定为非人类，直接拒绝——这道门防的是自触发循环。

// dsh-superagent-prototype · src/sources/feishu-trigger.ts
const mentioned = event.mentions.some(
  m => m.id === botId || m.id === botAppId
)

凭据同样隔离：gh-agent 与 lark-bot 各自独立配置目录，不碰个人账号。

这一页回答"安全吗"。三道门槛：身份（白名单）、意图（真 @）、来源（人类）。第三道是很多人会忽略的：机器人自己发消息不能触发自己。

代码片段是飞书侧的 mention 判断；人类判断在准入门里对所有 Source 生效。

12 MERGE AUTO AUTOactions

合并：把最后一步也交出去

仓库里加一个 GitHub Actions workflow，只处理 agent/* 分支的 PR，用 GITHUB_TOKEN 合并——合并者显示为 github-actions，而不是 Agent 自己。

# .github/workflows/auto-merge.yml
on: schedule: '*/5 * * * *'
if:  agent/* · non-draft · MERGEABLE
     · author == agent · no hold label
     · updated ≥ 180s ago
run: gh pr merge --squash --delete-branch

第一轮验证：PR #3 由 github-actions 合并，workflow 运行 15 秒。

风险与开关
  • 没有 CI 门禁时，PR 就绪即合并
  • 给单个 PR 加 hold 标签可暂停合并
  • 后续可加 build workflow，改成 --auto 等 CI 绿
  • 分支保护 + required review 是下一道保险

自动合并解决的是“最后一下点击”，不是“要不要 review”。两者要分开决策。

这一页讲取舍：自动合并很爽，但没有 CI 就是把评审压力后移。建议先跑一段时间，再决定是否加 required checks。

hold 标签是一个很实用的“紧急刹车”，演示一下怎么加。

13 LIMITS EDGE STOPhand back

哪些 bug 能交给它，哪些不能

适合交给它

  • 单模块逻辑 bug：边界、空值、异常分支
  • 可复现：有步骤、有日志、有期望行为
  • 最小改动：修一处，不动架构
  • 可验证：能跑测试、构建或对比截图

会主动停下来

  • 跨模块架构缺陷、需要重新设计
  • 需要产品决策的行为变更
  • 无法复现，且缺日志/环境
  • 需要线上权限、数据修复或发布操作

边界不是模型“做不到”，而是 scope prompt 和 Policy 主动设的护栏：宁可交回一张未完成草稿 PR，也不硬改。

实践建议：一条 bug 一张 Ticket；把复现步骤、期望/实际、不要改什么写进飞书消息里，成功率最高。

这一页管理预期：它擅长边界清晰、可复现、可验证的小 bug，不适合架构级缺陷和需要产品决策的变更。

如果听众要试，建议从测试环境的小 bug 开始，附上复现步骤和期望行为。
